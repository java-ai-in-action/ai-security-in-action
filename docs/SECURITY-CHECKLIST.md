# AI 应用安全自查清单（30 条）

> 上线前逐条过一遍。任一条打「✗」，就说明你的 AI 应用有已知的安全缺口。

## A. 输入侧（8 条）

| # | 自查项 | ✓/✗ |
|---|---|---|
| 1 | System Prompt 里有没有放任何「秘密」（接口名、内部规则、密钥）？ | |
| 2 | 用户输入有没有做长度上限（防超长注入 payload）？ | |
| 3 | 有没有敏感词 / 注入特征的前置拦截？ | |
| 4 | 用户输入有没有做语义隔离（包裹成「待处理问题」）？ | |
| 5 | 有没有按用户 / IP 做频率限制？ | |
| 6 | **多轮对话的历史消息**是否也做了同样校验？（很多人只校验当轮） | |
| 7 | 上传的文件 / 图片里的文本，是否也当作不可信输入？ | |
| 8 | 输入编码是否统一（防 Unicode 混淆 / 同形字绕过）？ | |

## B. 模型与提示（6 条）

| # | 自查项 | ✓/✗ |
|---|---|---|
| 9 | System Prompt 是否明确写了「任何情况下不得违反」的铁律？ | |
| 10 | 有没有用 role 区分「系统指令」与「用户内容」（而不是拼在一个字符串里）？ | |
| 11 | Prompt 里有没有硬编码的敏感数据？（有就是定时炸弹） | |
| 12 | 模型版本 / 温度等参数变更有没有走评审？ | |
| 13 | 有没有针对「角色扮演越狱」的约束？ | |
| 14 | 多 Agent 场景下，Agent 之间的消息是否也视为不可信？ | |

## C. 工具与执行（7 条）

| # | 自查项 | ✓/✗ |
|---|---|---|
| 15 | 每个工具是否都做了**参数校验**（类型、范围、格式）？ | |
| 16 | 文件类工具是否做了路径白名单 + 越界校验？ | |
| 17 | SQL 是否全部参数化（绝不拼字符串）？ | |
| 18 | Shell 是否用参数数组（绝不拼命令）？ | |
| 19 | HTTP 出站是否做了 URL 白名单（防 SSRF）？ | |
| 20 | 有副作用的工具（写、删、转账）是否要**人工确认**？ | |
| 21 | 危险工具是否**默认不注册**（白名单而非黑名单）？ | |

## D. 输出侧（5 条）

| # | 自查项 | ✓/✗ |
|---|---|---|
| 22 | 输出有没有做敏感信息审计（密钥、内部价、个人隐私）？ | |
| 23 | 命中敏感信息是「**拦截并替换**」还是「只记日志」？（必须前者） | |
| 24 | 报错信息是否脱敏（不要把堆栈、SQL、内部路径返回给用户）？ | |
| 25 | 流式输出是否也做了逐段审计？（别只审计完整响应） | |
| 26 | 有没有兜底话术？ | |

## E. 运维与审计（4 条）

| # | 自查项 | ✓/✗ |
|---|---|---|
| 27 | 每次工具调用是否全链路审计（谁、何时、调了什么、参数、结果）？ | |
| 28 | 安全事件是否有告警（异常拦截量突增要能发现）？ | |
| 29 | 密钥是否走 KMS / 环境变量（不硬编码）？ | |
| 30 | 有没有定期用「红队 Prompt」做回归测试？ | |

---

## 核心心法

> **AI 应用的安全，不是"让模型变聪明"，而是"让架构有边界"。**
>
> 绝不让模型「直接」决定有副作用的事情 —— 模型可以建议，执行必须由你的代码把关。
